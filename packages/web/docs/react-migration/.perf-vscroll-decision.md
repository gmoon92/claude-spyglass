## 1. 실측 데이터 규모 (근거)

### 1.1 MetaDocsCatalog — 카탈로그 전량 렌더

`MetaDocsCatalog`는 서버 fetch 결과 `rows` 전체를 한 번에 `<tbody>`로 렌더한다(`applyDisplayFilter`→`applySort` 후 `sorted.map`). 렌더 규모 = 카탈로그 항목 총수.

| 측정 | 값 | 명령 |
|------|----|------|
| `meta_documents` 총 행 | **112** | `SELECT COUNT(*) FROM meta_documents` |
| `v_meta_doc_usage` | 29 | `SELECT COUNT(*) FROM v_meta_doc_usage` |
| 타입 분포 | skill 93 · agent 18 · command 1 | `GROUP BY type` |

task 임계는 메타docs **N≥1000**. 실측 최대 112 → **9배 미달**. 가상 스크롤은 명백한 over-engineering. **변경 불필요 확정, 단서 없음.**

### 1.2 TurnRows — 활성 턴 1개의 행 집합

**핵심 사실**: `SessionLog`의 `<tbody>` = `TurnRows(activeTurn)` 이며, `TurnRows`는 **활성 턴 1개**만 렌더한다(`DetailView.tsx:206` → `SessionLog activeTurn={resolvedActiveTurn}`). 전체 턴이 아니라 **한 턴의 prompt + tool_call + response 행 수**가 렌더 규모다.

서버 `/api/sessions/:id/turns` 라우트(`packages/server/src/routes/sessions.ts:107~`)는 **LIMIT 없음** — `getTurnsBySession`(`packages/storage/src/queries/request/turn.ts:182`)이 turn당 모든 행을 반환하고 클라이언트가 전량 수신한다. 활성 필터(`ACTIVE_REQUEST_FILTER_SQL`, `read.ts:49`)는 `pre_tool`을 제거하나 `tool_name='Agent'`는 예외 보존.

활성 필터 적용 후 단일 턴 렌더 행수(`requests` GROUP BY session_id, turn_id):

| 측정 | 값 |

| 2위 / 3위 | 3816 (T1) / 1683 (T30) |

## 3. 그럼에도 react-window 가상 스크롤을 도입하지 않는 이유 (over-engineering 가드)

병목이 실재해도 **"react-window가 이 렌더 형태에 맞는 도구인가"**는 별개 게이트다. 세 가지 구체적 비호환이 "회귀 0" 게이트를 직접 위반한다.

### 3.1 semantic `<table>` + col-resize 계약 비호환 (★최대 위험★)

- `SessionLog`은 `<table>/<colgroup>/<thead>`를 **안정 노드**로 두고 `<tbody>`만 갱신한다(`SessionLog.tsx:94-117`). col-resize(`initColResize`)가 드래그한 컬럼 너비를 보존하는 계약(`.architecture-decision-session-detail.md` §4.2 ★최대 위험★).
- react-window(`FixedSizeList`/`VariableSizeList`)는 **스크롤 `<div>` 컨테이너**를 만들어 보이는 행만 렌더한다. `<tr>`을 `<table><tbody>` 안에서 가상화하면서 `<colgroup>` 너비 동기화를 유지할 수 없다 → `<table>` 의미구조 폐기 또는 `display:contents` 핵 필요. 둘 다 col-resize DOM 계약 파괴 = "부분 도입"이 아닌 구조 재설계.
- 검증 게이트 `session-log-colresize.test.tsx`가 colgroup/thead 마크업 불변을 단언 → 위반.

### 3.2 골든마스터 출력 동치 비호환

- `turn-rows-equivalence.test.tsx:144`은 **전체 행 집합** 바이트 동치를 단언: `tsx(<TurnRows turn/>) === js(makeTurnLogRows(turn))`. 마이그레이션 전략은 "동일 입력 → 동일 HTML 출력"(D형 골든마스터).
- 가상 스크롤은 **보이는 행만** 렌더(부분 DOM) → 윈도 크기 초과 턴에서 전체-집합 동치가 깨진다. task가 언급한 "가시영역 출력 동치"는 이 골든 게이트의 **시맨틱을 전체→가시영역으로 변경**해야 성립 = 기존 load-bearing 게이트 재작성.

### 3.3 chip-jump 동작 회귀

- `main.js` `handleChipActivation`/`findChipTarget`(`main.js:558-609`, `493-518`)은 chip-key/request-id로 **오프스크린 `<tr>`을 DOM 조회**해 스크롤·자동 펼침한다.
- 가상화된 오프스크린 행은 DOM에 없음 → `scrollToIndex` + 인덱스 매핑 재구축 플러밍 없이는 chip-jump가 동작 안 함 = "회귀 0" 위반.

### 3.4 단계/스코프 부정합

- react-window는 현재 **의존성에 없음**(`package.json` dependencies: react/react-dom/react-router/zod/zustand만). 의존성 추가는 빌드체인(W0)/별도 결정.
- stabilization 보드 W12-perf는 W10(router)·W11(strict) **이후** 순서. strict 전환(task #83)이 **in_progress** — strict 미완 상태에서 가상화 레이어를 얹는 것은 단계 부정합.

### over-engineering 3자문 (stabilization.md §6)
- **(a) 실제 결합/위험 감소 vs 간접 계층 추가?** → div-grid/display:contents 핵 추가 + 3개 계약 파괴. **순 위험 증가.**
- **(b) 분리 경계가 향후 변경을 쉽게? vs 그냥 이동?** → 새 경계 없음. 동작하는 semantic table을 깨지기 쉬운 윈도잉 레이어로 교체.
- **(c) 동작/테스트/출력 100% 동일?** → **아니오** — 부분 DOM이 골든 동치 + chip-jump 파괴. **하드 실패.**

→ 세 자문 모두 "변경 불필요(보류)"를 가리킴.

## 4. 권고 — 차기 W12-perf 사이클 (측정된 UX 문제 확정 시)

react-window가 아닌, **계약 보존 + 저위험** 순서로:

1. **`React.memo(RequestRow)` + `useMemo(rows 배열)`** — DOM/출력 변경 0, 측정된 재렌더 비용을 직접 절감. semantic table·col-resize·chip-jump·골든 동치 모두 무손상. **1차 처방.** (단, `RequestRow`는 llm-input·renderers-equivalence 골든이 공유 → 자체 게이트를 가진 별도 사이클로.)
2. **서버측 turn당 행 cap** — `/api/sessions/:id/turns`에 turn당 행 상한(예: 500) + "N행 더 보기" 점진 로드. 4683을 소스에서 제한, `<table>` 의미구조 보존. anomaly(spike) 표시는 cap과 무관하게 집계 유지.
3. **(최후) 행 가상화** — 1·2로 실브라우저 프로파일이 여전히 예산 초과일 때만, `<table>`을 div-grid로 재설계하는 **전용 페이즈**로 분리(골든 동치를 "가시영역"으로 재정의 + chip-jump scrollToIndex 재플러밍 동반).

본 task는 제목·스코프가 "가상 스크롤"이므로 1·2(memo/서버 cap)를 여기서 바로 도입하면 스코프 드리프트 → **권고만 기록하고 오케스트레이터가 W12에서 스케줄**.
