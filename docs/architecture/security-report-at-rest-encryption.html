검토일 2026-05-30 · 브랜치 stabilization/t05-metadocs-tests · 검토 방식: 소스 코드 직접 추적 + 전수 grep 검증
🔴
결론: 피드백은 정확하며 코드로 확정됨.
대화 본문(payload)과 system_prompts.content는 모두 암호화 없이 저장된다. proxy_requests.payload는 zstd 압축만 적용되고(암호화 아님, 키 없이 복원 가능), requests.payload·claude_events.payload·system_prompts.content는 평문이다. DB 파일 레벨 암호화(SQLCipher / PRAGMA key)는 전무(전수 검색 0건)하며, 유일한 보호 장치는 파일 권한 0o600/0o700뿐이다. 따라서 DB 파일이 유출되면 전체 대화·시스템 프롬프트가 그대로 노출된다.

2문제 지점 상세 — "어디가 문제인가"

치명적① proxy 요청 본문 — 압축만 하고 암호화 없음

프록시로 들어온 Anthropic API 요청 본문(전체 메시지 히스토리 + system + tools)을 zstd로 압축만 한 뒤 그대로 BLOB에 저장한다. 압축은 용량 절감일 뿐 보안 효과가 0이며, 키 없이 누구나 복원 가능하다.

packages/server/src/proxy/handler/inbound.ts:48–56 
// v21: 요청 본문 zstd 압축 — 암호화 아님
let payload: Uint8Array | null = null;
if (bodyBuffer && bodyBuffer.byteLength > 0) {
  payload = Bun.zstdCompressSync(new Uint8Array(bodyBuffer)); // ← 압축만, encrypt 호출 없음
}
packages/server/src/proxy/handler/persist.ts:108–111 
// v21: compressed payload
payload: ctx.payload,                          // 압축 BLOB 그대로 INSERT
payload_algo: ctx.payload ? 'zstd' : null,    // 값 범위: 'zstd' | null — 'encrypted' 없음

역방향 확인: routes/proxy.ts:55의 Bun.zstdDecompressSync(row.payload) 한 줄로 원문이 복원된다. 키·인증·복호 절차가 전혀 없다.

치명적② hook 원문 — 평문 JSON (압축조차 없음)

requests.payload와 claude_events.payload는 hook 원문을 JSON.stringify()한 평문 문자열이다. 컬럼 타입은 BLOB이지만 proxy와 달리 압축조차 적용되지 않아, strings 한 번이면 그대로 읽힌다.

packages/server/src/events.ts:82 (claude_events) / :275 (requests) 
payload: JSON.stringify(payload),   // ← raw hook payload 평문 직렬화

이 payload에는 last_assistant_message(Claude 응답 원문), 사용자 프롬프트, Bash/Read/Write 등 도구 입·출력, cwd·transcript_path 등 경로 정보가 포함된다. (인터페이스 RawHookPayload, events.ts:30–40)

치명적③ system_prompts.content — 평문 TEXT, API로 직접 노출

시스템 프롬프트 본문은 평문 TEXT 컬럼에 저장된다. hash는 SHA-256이지만 이는 중복 제거(dedup)용 PK일 뿐 본문을 보호하지 않는다 — 본문 content는 옆 컬럼에 그대로 있다.

packages/storage/migrations/022-system-prompts.sql:17–19 
CREATE TABLE system_prompts (
  hash     TEXT PRIMARY KEY,   -- dedup 키 (본문 보호 아님)
  content  TEXT NOT NULL,      -- 평문 본문
  ...
)
packages/storage/src/queries/system-prompt.ts — SQL_UPSERT 
INSERT INTO system_prompts (hash, content, ...) VALUES (?, ?, ...)
// content 파라미터를 아무 변환 없이 그대로 바인딩
노출 경로: GET /api/system-prompts/:hash (routes/system-prompts.ts:47–57)가 row 전체(=content 평문 포함)를 JSON으로 응답한다. 마찬가지로 GET /api/proxy-requests/:id/messages는 ①의 payload를 디코드해 메시지 원문을 반환한다. 두 엔드포인트 모두 인증 게이트가 확인되지 않는다 — DB 유출이 아니라 네트워크 접근만으로도 노출 가능.
치명적④ DB 레벨 암호화 부재 — 방어선은 파일 권한뿐

DB는 일반 bun:sqlite로 열린다. PRAGMA key / SQLCipher / cipher_* 설정은 코드 전체에서 0건이다 (전수 grep으로 확인).

packages/storage/src/connection.ts:74 
this.db = new Database(this.options.dbPath, { create: true }); // 평문 SQLite, key 없음

유일한 보호는 스키마 초기화 직후의 파일 권한 강화다 — 이는 같은 UID로 실행되는 다른 프로세스, 백업본, 디스크 이미지, 컨테이너 볼륨 복제에는 무력하다.

packages/storage/src/connection.ts:108 / :118 
fs.chmodSync(this.options.dbPath, 0o600); // 파일: 소유자 rw
fs.chmodSync(dbDir, 0o700);              // 디렉토리: 소유자만

DB 경로: ~/.spyglass/spyglass.db (connection.ts:18). WAL 모드 사용으로 -wal/-shm 보조 파일에도 동일 평문 데이터가 잔존한다.

3위협 시나리오 — "DB 유출 = 전체 노출"의 실제 경로

노트북 분실 / 백업 유출 / 컨테이너 볼륨 복제 / 같은 UID 악성 프로세스 ↓ (파일 권한 0o600 은 파일을 통째로 가져가면 무의미) spyglass.db 확보 ↓ sqlite3 spyglass.db — 키 입력 요구 없음 SELECT content FROM system_prompts → 시스템 프롬프트 평문 즉시 노출 SELECT payload FROM requests / claude_events → 대화·도구 I/O 평문 (strings 한 번) SELECT payload FROM proxy_requests → zstd 1회 해제로 API 본문 전체 복원

세 경로 모두 비밀번호·키·외부 의존성 없이 표준 도구만으로 완결된다. 압축은 진입장벽이 아니다.

4맥락 — 이미 알려진 한계인가

이 항목은 프로젝트가 이미 인지한 한계다. CLAUDE.md 최상단 세션 헤더에 동일 문구(대화 본문 비암호화 at-rest — payload BLOB·system_prompts 평문. DB 유출=전체 노출.)가 명시되어 있다.

즉 본 피드백은 새로 발견된 결함이 아니라, 문서화된 설계상 트레이드오프(로컬 단일 사용자 옵저버빌리티 도구로서 파일 권한에 의존)에 대한 재확인이다. 다만 API 엔드포인트를 통한 네트워크 노출 가능성(②③의 callout)은 "DB 유출" 프레임을 넘어서는 별도 표면이므로, 위험 평가 시 분리해서 다뤄야 한다.

5권장 조치 (우선순위)

  • P0  애플리케이션 레벨 암호화 — payload/content 저장 직전 AES-256-GCM 암호화. 키는 OS 키체인/환경변수로 분리. 압축(zstd) → 암호화 순서로 파이프라인 확장 (payload_algo='zstd+aes256gcm' 같은 메타로 추적).
  • P0  또는 DB 파일 암호화 — SQLCipher 전환 후 connection.ts:74 직후 PRAGMA key 적용. 단일 지점 적용이라 코드 변경 최소.
  • P1  본문 반환 API 인증 게이트 — /api/system-prompts/:hash, /api/proxy-requests/:id/messages에 인증/로컬바인딩 확인. (DB 유출과 무관한 별도 노출 표면)
  • P1  WAL 보조 파일 정리 — 암호화 미도입 기간에도 -wal/-shm 잔존 평문을 인지하고 종료 시 checkpoint/정리.
  • P2  기존 평문 데이터 마이그레이션 — 암호화 도입 시 적재된 평문 행 재암호화 또는 파기 계획 수립.
